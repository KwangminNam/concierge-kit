# ADR-0006. 요청 데드라인은 AsyncLocalStorage 가 아니라 헤더 레일 위에 올린다

## 맥락

요청 하나에 시간 예산을 주고, 그 요청을 처리하는 모든 백엔드 호출이 "남은 시간" 을 나눠 쓰게
하자는 제안이 있었다. 백엔드 세계의 deadline propagation 을 프론트 서버 층에 들여오는 것이다.
제안은 그 토대로 "요청 스코프" 라는 새 원시를 세우고, Next 에서는 AsyncLocalStorage 로 만들자고
했다. 프록시가 스코프를 열고 깊은 RSC 가 `scope.remaining()` 을 읽는 그림이다.

## 검증

playground 에서 프록시가 `AsyncLocalStorage.enterWith()` 로 값을 넣고 렌더가 `getStore()` 로
읽게 해 보았다. 같은 요청에서 헤더도 함께 재작성했다.

| 채널              | 렌더가 읽은 값 |
| ----------------- | -------------- |
| AsyncLocalStorage | `null`         |
| 요청 헤더         | 프록시가 쓴 값 |

프록시와 렌더는 별개의 비동기 컨텍스트다. 프록시는 응답을 반환하고 끝나며, 렌더는 그 연속이
아니라 라우터가 새로 시작한다. Next 에서 프록시와 렌더를 잇는 채널은 요청 헤더뿐이다.

## 결정

데드라인은 헤더로 건너간다. 새 원시를 세우지 않는다.

- 프록시가 절대 시각(epoch ms)을 내부 캐리어 헤더에 찍는다. 밖에서 들어온 값은 항상 덮어쓴다.
- 렌더는 `headers()` 에서 그것을 읽어 남은 시간을 계산하고, `AbortSignal` 을 만든다.
- `relay.forward()` 가 백엔드에 남은 시간을 상대값(ms)으로 보낸다. 두 기계는 시계를 공유하지
  않으므로 `grpc-timeout` 처럼 상대값이어야 한다.
- h3 는 `event.context` 가 요청 전체를 관통하므로 거기에 시작 시각을 둔다. 첫 호출이 시계를
  시작하고, `onRequest` 훅용 `stamp()` 도 둔다.

이것은 쿠키가 건너가는 방식과 같다. 프록시가 요청 헤더를 고쳐 쓰고 렌더가 읽는다. 데드라인은
릴레이 레일 위에 실리는 두 번째 화물이지, 릴레이가 그 위에 얹히는 토대가 아니다.

## 함께 검토했지만 뺀 것

같은 제안에 요청 상관 로깅, Server-Timing, 폭포수 감지가 있었다. 셋 다 "upstream 호출 기록" 이
필요하고, 그것은 fetch 를 가로채야 나온다. `relay.fetch()` 를 내거나 전역 fetch 를 패치하거나다.
설계 문서의 "하지 말 것" 에 fetch 래퍼가 있고, README 에 "fetch 는 필수가 아니다" 를 검증해
적었다. 셋은 그 결정을 뒤집어야 존재하므로 별도 ADR 없이 들어오지 않는다.

데드라인만 fetch 를 소유하지 않는다. `signal` 은 사용자가 fetch 에 넘기고 우리는 남은 시간으로
신호를 만들어 줄 뿐이다. 그래서 정체를 바꾸지 않고 들어온다.

## 결과

`deadline: { budget }` 정책 하나가 코어에 생기고, `forwardRequest` 가 쿠키와 데드라인을 함께
적용한다. 요청 헤더 전파(§6)가 들어올 자리도 이 함수다.
체감 효과는 제안보다 작게 적는다. Suspense 스트리밍을 쓰면 느린 호출은 자기 경계 안에서만
기다린다. 데드라인의 가치는 최악 시간을 상한하고 백엔드가 제때 포기하게 하는 것이다.
