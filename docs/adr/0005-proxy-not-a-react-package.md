# ADR-0005. 선언적 RSC 패키지 대신 프록시 어댑터를 만든다

## 맥락

참고한 선언형 라이브러리처럼 React 서버 컴포넌트용 선언적 API 를 낼지 검토했다.
후보는 쿠키 존재로 렌더를 가르는 `<Gate>`, 릴레이 정책으로 upstream 을 부르는 `<Query>`,
그리고 상태 코드 매핑이었다.

판단 기준을 먼저 세웠다. **명령형으로 불가능하거나 구조적으로 틀린가, 아니면 그냥 길기만 한가.**
참고 라이브러리가 값을 한 이유가 후자가 아니라 전자였기 때문이다. 훅은 조건부 호출이 안 되고
Suspense 경계는 컴포넌트여야 해서, 같은 컴포넌트 안에서 데이터를 받으면서 그것을 감쌀 방법이
아예 없었다.

playground 에 프로브를 만들어 RSC 가 실제로 무엇을 허용하는지 확인했다. 서버 컴포넌트 사이의
render prop 전달, 중첩 async 서버 컴포넌트의 `redirect()`, 렌더 중 쿠키 읽기 모두 동작한다.
즉 세 후보 전부 만들 수는 있다.

## 결정

셋 다 만들지 않는다. `@conciergekit/react` 패키지를 내지 않는다.
대신 `@concierge-kit/next` 안에 프록시 어댑터를 넣는다.

## 근거

- `<Gate>` 는 제약이 없다. `if (!store.has(name)) redirect()` 가 인라인으로 된다. 네 줄이 두 줄이
  되는 것은 이유가 아니다.
- `<Query>` 는 제약이 있다. 데이터 의존성마다 Suspense 경계를 만들려면 자식 컴포넌트가 필요하고,
  이것은 참고 라이브러리가 마주친 것과 같은 제약이다. 그러나 RSC 에서 우회가 싸다. 이름 붙은
  async 컴포넌트 하나면 되고, 클라이언트와 달리 상태를 꿰지 않아도 되므로 render prop 보다 오히려
  낫다. 제약은 있지만 대가가 없다.
- 상태 코드 매핑은 명령형으로 잘 된다. 반복될 뿐이다. 편의이지 원시 기능이 아니다.
- **렌더 중 쿠키 쓰기는 불가능하다.** 길어지는 문제가 아니라 못 하는 문제다. 그리고 이것을 할 수
  있는 계층이 정확히 하나 있다. 프록시가 응답에 `Set-Cookie` 를 실으면서 동시에 들어오는 `cookie`
  요청 헤더를 바꿔 쓰면, 뒤따르는 렌더가 브라우저가 보낸 적 없는 값을 읽는다. playground 와
  실제 브라우저로 확인했다.
- 그 동작이 정확히 양방향 릴레이다. 위로는 요청 헤더, 아래로는 응답 헤더를 한 지점에서 고쳐 쓴다.
  이 패키지가 라우트 핸들러에서 하는 일을 요청 전체에 대해 하는 것이다.
- 손으로 쓰면 틀리기 쉽다. 두 방향 중 하나만 하면 조용히 실패한다. 요청 헤더만 바꾸면 브라우저에
  쿠키가 안 붙고, 응답만 쓰면 이번 렌더가 여전히 옛 토큰을 본다. 둘 다 에러 없이 실패한다.
- 쿠키 값을 다뤄야 하는 유일한 지점이기도 하다. 요청 헤더를 갱신하려면 새 값을 알아야 한다.
  패키지 안에서 처리하면 사용자 코드는 여전히 값을 보지 않는다. 손으로 하면 사용자가 직접 파싱해야
  한다.

## 결과

`mergeIntoCookieHeader` 와 `removeFromCookieHeader` 가 코어에 들어간다. 프레임워크 무관한
문자열 연산이므로 h3 프록시(`nitro` 의 `onRequest`)에서도 그대로 쓰인다.
`onUnappliable` 의 경고 문구가 이제 실재하는 기능을 가리킨다.

Next 15 의 `middleware.ts` 는 기본이 Edge 이고 Next 16 의 `proxy.ts` 는 Node 가 기본이다.
코어가 Edge 안전하므로 둘 다 돌지만, 인스턴스 설정이 번들 경계를 넘지 않는다는 점은 문서에 남긴다.
